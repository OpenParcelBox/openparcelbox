# OpenParcelBox Principles

## English

### Local first

OpenParcelBox should work locally wherever possible.

### Self-hostable

Users should be able to run their own OpenParcelBox backend through the OpenParcelBox Cloud Community Edition.

### Open core

The core bridge, local protocol, access model, firmware foundation, API specifications and reference implementations should remain open and auditable.

### No artificial lock-in

Paid services should not be based on deliberately broken community features.

### Community benefit behind commercial features

Every major commercial direction should preserve or create meaningful community benefit, such as open specifications, documented APIs, self-hosting support, local operation, reference implementations or compatibility tools.

### Cloud where shared trust is needed

Cloud services may be appropriate where identity, routing, public locker discovery, push delivery, carrier coordination, certificates, plugin verification or trust registry functions require a shared layer.

### Owner-controlled access decisions

Access decisions should remain with the owner-controlled Core whenever technically possible.

### Secure by design

OpenParcelBox should be designed with security boundaries, least privilege, update safety, responsible disclosure and auditability in mind.

### Plugins request, Core decides

Plugins may request security-sensitive actions. The Core decides whether they are allowed.

### Commercial services for real value

Commercial services may cover operation, support, integration, certification, liability, security, hosting, updates and convenience.

### Brand protected, code open

OpenParcelBox code, documentation and hardware designs may be open under their respective licenses. The OpenParcelBox name, logo, certification marks and domain identity remain protected project identifiers.

## Deutsch

### Lokal zuerst

OpenParcelBox soll nach Möglichkeit lokal funktionieren.

### Selfhosting möglich

Nutzer sollen ihre eigene OpenParcelBox-Backend-Instanz mit der OpenParcelBox Cloud Community Edition betreiben können.

### Offener Core

Bridge-Core, lokales Protokoll, Zugriffsmodell, Firmware-Grundlage, API-Spezifikationen und Referenzimplementierungen sollen offen und überprüfbar bleiben.

### Kein künstlicher Lock-in

Bezahlte Dienste sollen nicht auf absichtlich eingeschränkten Community-Funktionen beruhen.

### Community-Nutzen hinter kommerziellen Funktionen

Jede größere kommerzielle Richtung soll einen echten Community-Nutzen erhalten oder schaffen, zum Beispiel offene Spezifikationen, dokumentierte APIs, Selfhosting, lokalen Betrieb, Referenzimplementierungen oder Kompatibilitätswerkzeuge.

### Cloud dort, wo gemeinsames Vertrauen nötig ist

Cloud-Dienste können sinnvoll sein, wenn Identität, Routing, öffentliche Locker-Verzeichnisse, Push, Carrier-Koordination, Zertifikate, Plugin-Prüfung oder Trust-Registry-Funktionen eine gemeinsame Ebene benötigen.

### Zugriffsentscheidungen beim Besitzer-Core

Zugriffsentscheidungen sollen, soweit technisch möglich, beim vom Besitzer kontrollierten Core bleiben.

### Sicherheit von Anfang an

OpenParcelBox soll mit klaren Sicherheitsgrenzen, minimalen Rechten, Update-Sicherheit, verantwortlicher Offenlegung und Auditierbarkeit gedacht werden.

### Plugins fragen an, der Core entscheidet

Plugins dürfen sicherheitskritische Aktionen anfragen. Der Core entscheidet, ob sie erlaubt sind.

### Kommerzielle Dienste für echten Wert

Kommerzielle Dienste können Betrieb, Support, Integration, Zertifizierung, Haftung, Sicherheit, Hosting, Updates und Komfort abdecken.

### Marke geschützt, Code offen

OpenParcelBox-Code, Dokumentation und Hardware-Designs können unter ihren jeweiligen Lizenzen offen sein. Name, Logo, Zertifizierungszeichen und Domainidentität bleiben geschützte Projektkennzeichen.
